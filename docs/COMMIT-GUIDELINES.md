## Git Commit Guidelines

Follow these rules for writing clear and consistent commit messages:

### The Seven Rules of a Great Git Commit Message

1. **Separate subject from body with a blank line**
2. **Limit the subject line to 50 characters**
3. **Capitalize the subject line**
4. **Do not end the subject line with a period**
5. **Use the imperative mood in the subject line**
6. **Wrap the body at 72 characters**
7. **Use the body to explain what and why vs. how**

No Conventional Commits prefixes (`feat:`, `fix:`). Plain English.

### Commit Message Template

```
Capitalized, short (50 chars or less) summary

More detailed explanatory text, if necessary. Wrap it to about 72
characters or so. In some contexts, the first line is treated as the
subject of an email and the rest as the body. The blank line
separating the summary from the body is critical (unless you omit
the body entirely); tools like rebase can get confused if you run
the two together.

Write your commit message in the imperative: "Fix bug" and not
"Fixed bug" or "Fixes bug." This convention matches up with commit
messages generated by commands like git merge and git revert.

Further paragraphs come after blank lines.

- Bullet points are okay, too
- Use a hyphen or asterisk for the bullet
- Wrap at 72 characters
```

### Good Examples

**Example 1:**
```
Add pricing page with contact button

List the plans on /pricing. Each plan ends in a Contact button that
opens the contact form with the plan preselected.

Why: There is no online payment yet, so a sale starts with a message.
```

**Example 2:**
```
Move hero copy into a content file

Read the home page text from src/content instead of hard-coding it
in the component.

Why: Copy changes should not need a component edit.
```

### Bad Examples

- **Too vague:** `Update files`
- **Not imperative mood:** `Fixed the layout bug`
- **Subject too long:** `Add new page that shows every app we sell with screenshots and prices`
- **No body for complex changes:** `Refactor layout`
- **Subject ends with period:** `Add contact page.`

### Grouping Commits by Changes

**Always group related changes into a single commit.** Do not mix unrelated changes in the same commit.

- **One concern per commit**: a bug fix, a feature, a refactor, or a style change should each be its own commit
- **Group files that change together**: if a page needs a new component, commit them together
- **Separate cleanup from features**: don't sneak formatting into a feature commit
- **Commit in logical order**: if B depends on A, commit A first
- **Group by change type, not by file**
- **Version bumps get their own commit**: `Bump version to X`

### When to Write Detailed Commit Bodies

Write a detailed body when:
- The change is not obvious from the subject line
- The change affects multiple files or areas
- You're introducing a new pattern or approach
- The reasoning behind the change is important

### Multi-Line Commit Messages (MCP Tools / Programmatic Commits)

When the tool's message parameter does not support real newlines, **never use literal `\n` escape sequences**. They are committed as-is and produce broken output. Write the message to a temporary file outside the repo and use `git commit -F <file>`:

```bash
git add src/pages/pricing.astro
git commit -F /tmp/msg.txt
```

Commits made with Claude end with a `Co-Authored-By` line.

### Author

Commits carry the person's own name and email as author, never a bot identity such as `Claude <noreply@anthropic.com>`.
Check `git log --format='%an <%ae>'` before pushing. If the machine's git config is a bot identity, commit through a
tool that authors as the signed-in GitHub user, or set the author explicitly with `git commit --author`.

### Branches and history

Never commit straight to `main`. Work on a plainly named feature branch and leave the merge to the person.

`main` keeps one straight history line. Keep the branch rebased on `main`, and merge by fast-forward or rebase only, never with a merge commit.
